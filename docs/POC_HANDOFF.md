## 啟動

在專案根目錄雙擊 `Play.cmd`。開發時雙擊 `Open-Editor.cmd`，或用 Godot 匯入 `godot/project.godot` 後按 F5。

本機已備妥官方 Godot **4.7.2.stable.official.ed1daf0bf**，位於 `.tools/godot/`。這個目錄不提交 Git；新 checkout 可執行 `./tools/install-godot.ps1`。也可傳入既有 Godot 路徑：

```powershell
./tools/godot.ps1 -Mode play -GodotPath 'C:/path/to/Godot_console.exe'
```

Windows 啟動腳本把遊戲資料放在專案 `.tools/userdata/`，驗證 runner 使用獨立的 `.tools/test-userdata/`，編輯器使用 self-contained 模式。字體使用系統的 Microsoft JhengHei／Noto Sans TC，未加入外部美術或字體資產。

## 5–10 分鐘人工驗證步驟（M 尚待人工驗收）

1. 使用預設 Seed **1106**，先保持 1×。初始有 32 位真實居民、8 戶家庭、0 個已建立聚落。觀察家庭活動、糧食祈求與自主形成聚落。關閉「夜間快進」時，1 個模擬天約 8 秒。
2. 約第 3 個模擬天會出現可接收神諭的聖者。祭司是另一種職務，不因任職就能接收神諭。
3. 在「降雨」分頁選快速設定；中心預設 `(24, 26)`，半徑 9、強度 1、持續 12 天。可點地圖調整中心。查看 DP、臨在與冷卻預覽後按「施放降雨」。初始標準施放成本 24 DP、冷卻 30 個模擬天。
4. 切換「神諭」，向選定聖者傳達 `food.produce`。不指定居民職業、行動或產量。查看收到、聽見、接受／暫緩、嘗試與產出階段。
5. 切換地圖到「土壤濕度」與「未收穫作物」，點選居民或右側居民選單，查看工作評分、神諭壓力、可行資源、決策理由，以及家庭／共用庫存的差異。
6. 讓時間繼續，觀察實際收穫與祈求改善。只有可信且真正改善的需求才增加持久虔誠；強度跨越貢獻級距後，後續 DP 恢復率提高。點選世界紀錄的事件連結查看直接父事件與實際採用的理由。
7. 測試重複神諭、降雨冷卻、暫停、加速及存讀檔。拒絕理由應可理解。神諭普通成功不會自動結束，需到期、聖者死亡或按「宣告此神諭結束」。

這是觀察流程，沒有自動施放、腳本保證豐收或強迫居民執行。需求可能自行解決，神諭也可能延後住房等其他工作。人工需評估是否能理解這些取捨；機器操作檢查不能代替 M。

### 白天觀察與夜間快進

預設開啟「夜間快進」：20:00–08:00 以所選倍速再乘 8 前進，08:00 恢復所選倍速。夜間出生／死亡、孕育、搬遷、持續缺糧、聚落形成、聖者／祭司出現、祈求改善及重要 Rain／Oracle 事件會在該次排程的實際時間暫停，顯示事件原因。每次按「繼續」後有 **10 秒實際播放時間**的緩衝，期間事件照常記錄，不自動暫停；緩衝結束不補播舊暫停，之後的新重大事件恢復暫停。手動暫停會凍結緩衝倒數。一般施工、生長、傳播與嘗試紀錄不會打斷快進。可隨時關閉快進觀看晚間，手動暫停仍停止所有時間。

地圖優先顯示白天仍在活動的居民；休息者仍存在於模擬中，可從右側選單查看。選定居民及夜間事件的在世參與者保留標記。畫面顯示時分與日夜，夜間略調暗地圖。這是呈現與觀察節奏的調整，沒有修改作息、產量、人口或信仰規則；快進仍執行每個排程與精確到期事件。

### 食物保障與既有活動的取捨

已跟隨 pull 下來的新版規格修正共用食物存取與決策路徑。家庭資格同時檢查聚落歸屬、成員名單、既有聚落距離與可通行路徑；搬遷同步更新家庭與居民歸屬。隔離家庭保留自己的實際新產出，不將食物存進無法取用的共用庫存。消費先用私有食物，再向可到達的真實共用庫存請求缺口，短缺時按請求比例分配。

工作、祈求與生育使用同一份可取得食物估算。共用份額按在世成人／小孩的實際每日需求分配，僅作規劃估算，不移動或重複計入庫存；實際提領仍受現有存量限制。家庭儲備目標沿用 4.5 天、聚落保障目標沿用 6 天。食物技能與 `food.produce` 對工作評分的加成隨實際食物需求降低，居民可轉做現有的建造、材料採集與家庭照護；缺口出現時食物工作優先度恢復。神諭仍保持有效，不強迫工作或保證產量。

本次沒有調整土地肥力、作物產量、成人／小孩消耗量、生育機率或既有 20:80 新產出分配比例，也沒有新增活動。居民檢視器顯示自有食物、可取得共用份額及保障天數，工作原因附上真正評估的時間與輸入。世界紀錄顯示重大事件；個別神諭接受／暫緩／嘗試等因果資料仍可從相關檢視器查看，例行施工與食物總量不寫入 History。

## 效能數據的解讀

本次最終單獨執行的 Windows headless 結果（Godot 4.7.2、Seed 1106、規則 mvp0-3）：

| 人口 | 模擬天數 | 耗時（秒） | 模擬天／實際秒 | 追蹤記憶體（MiB） | 到期 backlog |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 32 | 90 | 8.438 | 10.667 | 30.26 | 0 |
| 1,000 | 3 | 2.122 | 1.414 | 37.95 | 0 |
| 10,000 | 3 | 18.905 | 0.159 | 106.18 | 0 |

32 人探測的環境 dispatch 約 6.246 秒、個人決策約 2.061 秒；10,000 人探測的個人決策約 17.167 秒。食物存取估算在工作批次統一計算；尚未加入大人口優化。完整各系統計時見 JSON 證據。

各 runner 會重產生 `godot/test-output/acceptance.json`、`food-integration.json`、`benchmark.json`、`ui-preview.png` 與 `ui-night.png`，該目錄不提交 Git。交接的 `docs/evidence/` 保存本次結果。

系統計時以 `Time.get_ticks_usec()` 包住模擬 dispatch，為單執行緒區段耗時的 CPU 工作近似值，未包括初始化、所有排程／精確期限檢查、呈現副本與渲染。記憶體是 `OS.get_static_memory_usage()` 的 Godot allocator 追蹤值，並非 Windows 整個程序的 working set。大人口是探索性密集配置，只跑三天，不能推論長期或 10k 即時遊戲效能。
