# Divine Powers Expansion v0.1 — Web PoC v2

**Status:** **Implemented in the modular Web PoC v2 (2026-10-11)**. Direct functional checks are added under `tests/divine-powers.test.cjs`; this is a playable experimental slice, not a claim of final balance, multi-God or real-browser visual acceptance.

**Target:** `main/poc/v2/` (modular browser PoC). The formal v1 contracts under `main/docs/` remain authoritative. Baseline: Priest Interaction v0.2 confirmed playable, existing `rain` Miracle and `food.produce` Oracle.

## Player-facing objective

Before introducing the second religion, give the player meaningful distinct actions: improve farming, rescue the injured, briefly empower believers, exert environmental pressure, inflict immediate harm, temporarily disrupt enemy work/organization/perception, and *actively direct* the existing autonomous Priest network toward propagation. Avoid waiting-only gameplay or extra complexity added solely to increase the power count.

## Implemented first batch: eight Miracles and one Oracle

Preserve existing `rain` and `food.produce` behavior. **Do not introduce an unlock tree** in the Sandbox PoC.

## Explicitly excluded: `food.reserve`

User decision (2026-10-11): **If Food Reserve cannot deliver a meaningful gameplay difference from Food Production, omit it.**

Current PoC already has autonomous household/common food stocks, a physical-access allocation model and granary building. Merely boosting farming/foraging would be equivalent to `food.produce`. A distinct reserve policy would require credible extra behavior (e.g. real rationing rules, loss/spoilage avoidance, transport, deliberate stock/allocation policy) and would touch multiple economic constraints. **Do not implement `food.reserve` in this batch, do not expose it as a disabled UI placeholder, and do not replace it with a filler Oracle.** Revisit only if the supporting food-logistics simulation makes the two play strategies observably different.

## Mechanics and authority boundaries

### Miracles

- All casts are **manual**, with center, effect area, intensity / applicable duration, pre-validation, global DP spending, independent skill Mastery (Lv1–Lv5) and per-skill cooldown. Invalid attempts do not charge or mutate authoritative state.
- The direct effect is reliable if valid; benefit/harm, resource conservation, autonomous activity and durable Devotion emerge from owning World / Individual / Religion systems.
- **Ripening (first agricultural implementation priority, implemented):** the current Agriculture profile stores a finite per-field `cropStock` with real daily growth constrained by moisture/fertility, a capacity equal to roughly 2 best-season growth days (`cropStockCapacityDays: 2`), and harvesting that subtracts actual stock. When harvesting depletes fields faster than they replenish, Ripening should directly improve **only the replenishment/maturation rate of real growing crop stock** for the chosen effect duration (and analogously the Original model's `crop` growth). Keep the same base finite stock cap and ordinary climate/land feasibility. The result is faster availability of future crops, **not** a direct change in human work speed, a new farming action, permanent global yield tuning, or free stored Food. A separate discrete maturity clock is NOT needed for this first PoC; use the actual continuous crop stock with bounded effect inputs.
- **Harvest:** increase real harvestable output of existing crops per harvest or reduce crop loss *without speeding the regeneration timer/rate*. **Do not implement Harvest as another multiplier on the same `cropStock += daily` growth formula.** Multiplying worker collection capacity alone is ineffective while crop stocks are depleted. Its additional crop yield must have physically traceable standing-crop stock or an equivalent accounted field-level source before any actual labor moves Food into household/public inventory. If this cannot be demonstrated as a meaningful distinct action in the current continuous-stock model, defer Harvest independently; do not block Ripening. A world without existing applicable fields cannot create Food.
- **Heal:** target currently living individuals in range and only change real health/recovery state; normal cap applies. Health can decrease again from genuine subsequent causes. Evidence/faith is conditional on answered needs, not per-cast.
- **Efficiency:** on successful cast, give **present, living followers of the caster's religion (Devotion >= the configured follower threshold, initially 40)** a bounded, timed individual enhancement. It increases *real output per feasible action*: harvesting/gathering remains capped by source stock, building still consumes materials, and Priest sermon quality can improve **only where a real sermon/contact occurs**. No free inventory, occupation assignment, direct conversion, automatic DP, or reward for simply being buffed. Do not automatically grant the status to future arrivals; only current eligible targets receive it, and only while they remain aligned with the caster. Distinct from Heal (repairs existing health) and future Ripening（促熟） (advances crop maturation, without directly making people work faster).
- **Drought:** first-pass maximum cast duration one simulated month and baseline cooldown one simulated month, both tunable (matching Rain's agreed envelope). Rain and Drought are separate skills with separate XP/cooldowns and independent active inputs, *not mutually cancelling flags*. Net weather/soil outcomes arise via the existing moisture model. Expiration stops the input, not the resulting damage.
- **Lightning:** finite area / strength, with immediate damage through Individual health/death rules. Lightning need not invent a Wildfire propagation system in this slice.
- **Confusion:** timed cognitive interference in **currently affected living people**, for example a bounded reduction in consistency among otherwise feasible autonomous choices, and impaired Priest/Oracle communication reliability when those individuals genuinely preach/relay. It changes decision inputs or communication effectiveness, **not their faith identity, mortality, permanent Devotion or an RTS-style forced command**. The ordinary decisions still obey feasibility, resources and deterministic simulation.
- **Blindness:** timed sensory impairment in **currently affected living people**, specifically reduce perceptual reach or effective local discovery used by resource-search/field-search and perception-dependent work paths. It need not invent global line-of-sight, tactical vision or a combat kernel. Preserve the authoritative household/common-food **physical-access** policy; blindness must not arbitrarily delete stored food or treat a legitimately eligible household as geographically cut off. Preserve audible sermons / received communication unless a real visual prerequisite exists.
- **Effect targeting and friendly fire:** Efficiency explicitly selects the caster's own present followers as a beneficial attunement; offensive area casts (Lightning, Confusion, Blindness) **do not magically spare one's own followers**. A specific selected individual may be a valid offensive target where supported, but no blanket faction-based immunity is introduced. A debuff's final consequences may affect religion indirectly, never by silently modifying Devotion.
- **Status storage and expiry:** Efficiency/Confusion/Blindness apply bounded, individually inspectable **temporary statuses** to currently affected real people, expiring in simulation time. No unbounded stacking via repeated casts: same-type overlap refreshes or takes the strongest within a cap (choose one consistent, configurable rule); different types may coexist and their consequences remain causally observable. Status clocks are included in save/replay and expire after Saint/Priest migration normally. Casting remains manual, cooldown and independent Mastery per Miracle.
- **Spatial capability:** full-game design requires cast-center density and dominance for high-tier offensive/destructive effects (initial dominance strictly above 50%, plus adequate density), while low-tier support is more accessible. In particular, Confusion/Blindness of meaningful strength are offensive even without instantaneous HP damage. Classify by actual direct effect and magnitude. The current PoC represents only one actual player God; do not counterfeit full rival dominance calculations or silently waive future high-tier policy. Expose any deliberately simplified PoC eligibility policy and cover zero-presence and insufficient-density rejection.
- Never treat radius overlap with rival land as per-target recertification: validate **only the cast center**, then apply real effects to everyone in range.

### `religion.spread` Oracle

- Only an eligible **Saint** receives the initial Oracle, using the existing per-Saint quota, active-type lock, issue/expiry/conclusion/death lifecycle. Priests relay; they do not directly receive raw Oracle by holding office.
- The intended decision is **more preaching effort**, especially when available Priest leisure time can be used for it. Existing autonomous Priest preaching stays active without Oracle.
- The new Oracle contributes bounded context-aware priority or opportunity to the **existing preaching choice** (and ordinary relay), never a god-issued occupation/order or a free worldwide conversion probability.
- Any religious growth must follow **actual recent sermon/contact**, receptivity and existing conversion policies: normal Priest activity may attract unaffiliated people and gradually challenge only low-Devotion rival affiliation. Established 40+ rival Devotion remains resistant to ordinary preaching.
- Effects must expire naturally with the Oracle's assignment. Sermons already delivered and real affiliations already changed are not reversed.
- Overlapping different Oracle intent types may coexist; *different types must not inherit the hard-coded `food.produce` work bonus or fulfillment reward*. In the current kernel `workCalling()`, `checkFulfillment()`, `processOracles()`, and UI each currently assume the one-food-Oracle case. Filter by canonical intent when extending them.

## Required acceptance cases

1. **No-op/rejection:** out-of-bounds, insufficient DP, cooldown, inadequate destructive capability, dead target / missing applicable field etc. are accurately handled; rejected command does not charge and a cast never silently yields fake stores or followers. For cases where empty-target casting is intentionally permitted, expose a truthful no-applicable-target warning.
2. **Ripening direct behavior (no A/B required):** begin with a valid real field whose `cropStock` was harvested close to zero; issue one eligible Ripening. Its crop stock must replenish through the existing physical crop growth step with the Miracle's configured multiplier while retaining the normal finite cap and soil/moisture constraints. No stored Food is created on cast. After the specified simulated-time expiry, the multiplier stops without erasing standing crops. The Original model's continuous `crop` path remains valid.
3. **Harvest, Ripening and Rain direct invariants:** Harvest adds bounded physically stored standing-crop biomass proportional to **already existing** crop stock, never household/settlement Food. Standing harvest-blessed stock may temporarily exceed the ordinary replenishment cap and must persist until collected, without further regeneration above that cap. Ripening modifies future field replenishment *rate* but not ordinary capacity; Rain modifies moisture. Verify these mechanisms directly via the existing state changes and inventory conservation, not an A/B balance experiment. If Harvest loses its distinguishable output semantics later, hide/defer Harvest independently.
4. **Heal:** at least one genuine injured survivor improves; an unwounded or deceased person is not spuriously healed or resurrected.
5. **Efficiency:** eligible committed followers receive an actual temporary action-output modifier at the existing gathering/harvesting/construction transfer or progress step; physical resource stocks and building materials remain conserved. Existing injured persons are not healed; crop replenishment is not accelerated; non-followers, future arrivals and former followers gain no ongoing benefit. Priest improvements require real sermons/contacts.
6. **Confusion vs Blindness:** Confusion modifies only bounded feasible-decision scores and actual sermon effectiveness but **not perception distance**; Blindness narrows per-person resource/field discovery and practical harvest reach without introducing generic decision randomness. Statuses expire in simulated time, do not directly change Devotion, and do not force specific work. Competing-religion fixtures show an observable short-term impairment; offensive area casts may also affect nearby friendly residents. If Blindness cannot yet exercise actual perceptual work paths, defer it rather than shipping a cosmetic-only alternative to Confusion.
7. **Drought / Rain:** simultaneous input is deterministic through the soil model; each expires at its own simulated deadline; damage persists as world state.
8. **Lightning:** damaging cast changes living health or actual death with valid provenance; friendly religious affiliation offers no protection; no disconnected fire or fabricated damage layer.
9. **Religion Spread:** an issued and propagated Oracle must record real additional leisure sermons and real contact-driven religious transmission. Without a living qualified Saint/actual preacher, it must never invent worldwide conversions. Ordinary Priest preaching continues without Oracle, and Devotion 40+ rival affiliation remains protected from this mundane channel.
10. **Oracle ownership:** same-Saint same-type lock, independent types, quota, expiry, conclusion and owner death work. Spread must **not** increase food-work Calling or receive food fulfillment faith credit.
11. **Integration/UI:** selecting any visible ability uses that ability, not Rain or `food.produce` by mistake. Cooldown/DP/quota disable the correct button. Cast preview and final charge agree; fixed viewport, hints and Priest petition bubble remain intact. Mocked DOM route checks are not a substitute for running a real-browser visual test.
12. **Regression:** `npm test`, `npm run smoke`, `npm run check:agriculture` are the checkout commands to execute. Direct JavaScript execution has already passed all 8 new functional cases and 35 selected legacy functional regressions and 6 UI/source layout checks; the actual local npm commands and real-browser layout screenshots have **not** been run in this remote GitHub editing session. Seeded save/restore and legacy migration must preserve history, independent cooldowns, Mastery and remaining temporary-status time.

## Scope limit

This is an incremental **implemented Web PoC experiment**, not a final power taxonomy or multi-God simulation. Protect existing agriculture balance, Priest behavior and determinism. More Miracle types (Protect, Wildfire, Storm) and other Oracles remain later candidates. **Ripening (formerly Accelerate) is implemented and deliberately prioritized before Harvest** because real `cropStock` can deplete quickly; Harvest now increases bounded existing standing biomass immediately, while Ripening accelerates future crop replenishment. Full rival-Dominance calculation, territory infrastructure, explicit eyesight/LOS, and fully calibrated DP costs are not claimed. No additional A/B balance run is required for this agreed slice.

Confusion temporarily degrades relevant sermon credibility; Blindness narrows current residents' actual perceptual farming/gathering reach.
- The current single-God Web PoC uses a **simplified own-Presence weighted density gate** for offensive casts. It does **not** pretend to compute a real 2-God dominance fraction; final religion competition and spatial qualification remain a later architecture milestone.
- Direct behavior was verified via executed JavaScript with **10/10 new feature cases** and **35/35 selected existing simulation regression cases, plus 6/6 existing UI/source layout checks**; simple simulated-browser interaction exercised Ripening map casting and Religion Spread issuance. This does **not** constitute full Node npm test-suite execution, automated live browser screenshots, or a cross-seed A/B balance exercise.
